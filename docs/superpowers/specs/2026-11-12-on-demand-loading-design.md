- 日期：2026-11-12，基準提交 `ff4045a9`（`staging`，19.5.0）
- 狀態：**設計，等 Allen 確認 §9 的決定後才動工。這份文件沒有改任何程式。**
- 接續：`2026-10-06-split-storage-design.md` §6 第 1 項（「按需載入」，當時列為另寫設計）與 §11 的結論（「要讓峰值再大幅下降，剩下的辦法是不要在啟動時把所有附件讀進記憶體」）。
- 負責：資料與同步是 Allen 主責。本設計改變「對話在記憶體裡的樣子」，照協作規則要先在 Linear 寫一則相容性說明（label `contract`）由 Allen 確認（§10）。

## 1. 目標與非目標

**目標**
1. 啟動時記憶體與時間跟「對話總量」無關：只讀標題清單（存根），點進對話才讀訊息與附件。
2. 記憶體裡同時有訊息的對話只有：正在用的、最近開過的幾個、正在回覆或有未存變更的。
3. 儲存不寫存根（沒讀進來的對話永遠不會被誤寫、誤刪）。
4. 使用者看得到的行為不變，除了：第一次點進很久沒開的對話，多一個很短的讀取（本機 IndexedDB，預期幾十毫秒）；全文搜尋與全部對話的統計第一次可能慢一點並顯示進度。
5. 舊資料零損失、可退回，旗標控制，先上 `staging`。

**非目標**
- 不改雲端資料模型、不把本機的舊對話刪掉改成只留雲端（見 §9 決定 1：本機仍全存，只是不一次讀進記憶體）。
- 不改訊息本身的資料格式。

## 2. 現況（事實）

來自程式與 2026-10-06 的量測（那次量測這次沒有重跑）：

- 儲存已經是每個對話一筆（`workspace-store-v2.js`），附件另存（`…_att_<id>`）；索引 `meta` 每個對話只有 `fp`（指紋）、`size`、`updatedAt`、`atts`。
- 但 `load()` → `readAllRecords()` 把**所有**對話與附件讀進記憶體，交給 `normalizeLoadedLegacyAppData` 再放進 `runtimeAppDataStore.conversations`（一個普通陣列，`kernel/app-data-store.js`）。
- 資料 46 MB 時啟動峰值約 580–750 MB，98 MB 約 910–960 MB；其中約 145 MB 是 IndexedDB 讀進來必然的配置。
- 儲存時 `save()` 對每個對話都編碼並算指紋（完整掃描 150 個對話 38 毫秒，已量過），沒變的跳過。
- 讀 `.messages` 的檔案約 80 個，讀 `getConversations()` 的約 36 個，雲端同步 `cloud-sync-v2-*` 共 3464 行。
- 程式裡已經有一個相近的概念：`cloud-assets.js` 的 `hydrateConversation`（雲端對話的附件按需補回）。

## 3. 核心設計

### 3.1 存根（stub）

不在記憶體的對話用**同一個物件**表示，不另外建一種：

```js
{ id, title, createdAt, lastUpdatedAt, model, provider, folderId, archived, pinned, deletedAt, retentionMode, ...（除 messages 以外的所有頂層欄位）,
  messages: EMPTY,            // Object.freeze([])，改它會丟 TypeError（模組是嚴格模式）
  __stub: true,               // 沒讀進來
  __count: 128,               // 訊息數
  __flags: { council: true, ... } // 側欄與列表需要、本來要掃訊息才知道的少數事實
}
```

- **保持物件身分**：讀進來（hydrate）時**就地**把 `messages` 與其他欄位填回去、拿掉 `__stub`，不換物件，所以到處被拿著的引用（側欄、閉包）都看得到。收回（evict）反過來就地清空。
- **防呆**：存根的 `messages` 是凍結的空陣列，漏改的地方是「寫入時丟錯」而不是默默讀到空；儲存層拒絕寫入 `__stub` 物件；新增測試掃原始碼找 `getConversations()` 結果的 `.messages` 讀取（有白名單）。

### 3.2 存根記錄（儲存格式，只增不改）

- 每個對話寫入時，在**同一個交易**多寫一筆 `…_stub_<id>`（上面那個物件的 JSON，約 1–2 KB）。為什麼不放進 `meta`：`meta` 在每次儲存都整份重寫，1000 個對話每次多寫 1–2 MB；單獨一筆則只在那個對話變動時才寫。
- `meta.conversations[id]` 加一個選用欄位 `stub: 1`（有存根記錄）。`WS2_VERSION` 不變，舊程式讀到多餘欄位與多餘的 key 都會忽略（要在 P0 用舊版程式實測確認，這是退回的前提）。
- 載入：讀 `meta` → 每個有 `stub` 的 id 讀 `…_stub_<id>`（批次，沿用 `readItems`），沒有 `stub` 的走原路（讀完整記錄）並**排入背景補寫存根**（一次一個，逐步補齊，不阻擋啟動）。所以第一次啟動新版和舊版一樣慢，補完之後才快；補寫失敗只記警告。
- 存根只含頂層欄位與少數摘要；`__flags` 在編碼時從訊息算出來（例如 `isCouncilConversation` 現在要掃訊息、`temporary 且 messages.length === 0` 這類判斷）。

### 3.3 讀進來（hydrate）與收回（evict）

- `ensureConversationsLoaded(ids)`（新，放 `workspace-store-registry` 旁）：從儲存讀完整記錄（含附件、套用與現在載入時相同的單筆正規化）填回物件；同一個 id 同時被要求只讀一次（共用 promise）；在儲存的獨占鎖之內讀，所以不會讀到寫一半的記錄。
- 進入的地方：切換到對話、`reattach`（伺服器回覆回來）、分支、分享、匯出、垃圾桶檢視、封存檢視、專案對話檢視、引用等「用 id 打開一個對話」的動作，一律 `await ensureConversationsLoaded([id])`。
- 收回：LRU，保留最近 N 個（預設 5，§9）；**不收回**：正在顯示、正在回覆（`__astraPendingResponse`、`getAbortController`）、有未存變更（指紋與儲存不同）、被伺服器回覆或研究執行引用的。收回前先確認已存。
- 儲存時存根完全跳過編碼與比對，所以儲存比現在更快。

### 3.4 兩個分頁

儲存層已有 Web Locks 協調（`workspace-storage-coordinator.js`）。新做法讓一個分頁**不再有機會覆寫它沒讀進來的對話**，比現在安全。另一個分頁改了某個對話時，這個分頁的存根或已讀進來的內容可能過時：沿用現有的「儲存時指紋變了」偵測，加上一個「這個對話在別處被改過，下次打開重讀」的標記（P0 要讀 `mergeStaleLegacy` 與多分頁相關測試確認現況）。

## 4. 所有讀對話的地方，分三類

| 類 | 需要什麼 | 例子 | 處理 |
|---|---|---|---|
| A 只要欄位 | 標題、時間、置頂、封存、專案、刪除時間 | 側欄歷史、專案對話列表、垃圾桶列表、批次選取、資料夾、移動、封存、`isSharedProject`、`conversationExists` | 存根就夠，改成「存根安全」，加測試 |
| B 開一個對話 | 該對話的全部訊息 | 切換對話、回覆管線（約 50 個檔案）、`reattach`、分支、分享、引用、單一匯出、垃圾桶／封存／專案檢視、視覺檢查 | 進入點 `await ensureConversationsLoaded`；回覆管線本來就只動目前的對話 |
| C 掃所有對話的訊息 | 全部訊息 | 全文搜尋、使用量圖表、時間分析、dashboard、記憶系統的歷史索引（`page-history`、`page-rebuild`、`history-index`）、專案影片來源（`chatVideoSourcesOf(getConversations())`）、匯出全部、P2P、雲端同步的套用 | 見 §5，逐項處理 |

## 5. C 類逐項

- **全文搜尋**（`search-upload-sidebar-lifecycle.js`）：先用存根的標題立刻出結果；內文用**串流掃描**（分批讀記錄、解析、比對、丟掉，記憶體只多一批），結果隨到隨顯示並有「還在找」。若實測太慢（對話很多時），再做持久化的搜尋索引（另開一階段，不在這份設計）。
- **使用量／時間分析／dashboard**：串流彙總（一次只在記憶體放一個對話），結果快取在記憶體（修改時失效）。第一次開這些畫面稍慢並顯示讀取中。之後如果要常駐，再把彙總（每模型次數、小時分布）放進存根。
- **記憶系統歷史索引**：本來就是逐筆處理對話，改成逐筆從儲存讀、處理、丟掉；與 2026-10-30 記憶重做計劃相容。
- **專案影片來源**（`project-pieces.js`）：存根的 `__flags` 記「這個對話有影片」；打開專案頁時才逐個讀有影片的對話。
- **匯出全部／P2P**：逐筆讀、寫進輸出、丟掉（現在是整份轉 JSON，這裡同時降低匯出時的峰值）。
- **雲端同步**（風險最高，7 個檔案直接讀訊息）：
  - 寫入路徑（`beforeWrite` 的 `changedConversationIds`、`readPreviousConversations`）**本來就只碰改過的對話**，而改過的對話一定在記憶體，所以不變。
  - 套用遠端（`cloud-sync-v2-merge`、`cloud-workspace-live-lifecycle` 的 `applyWorkspace`）：遠端更新一個**沒讀進來**的對話時，若本機自上次同步沒有未同步的變更（journal 可判斷），直接把遠端版本寫成記錄並更新存根，不讀進記憶體；有未同步變更才讀進來走現有的合併。**這一段要在 P0 把 7 個檔案讀完才能定案**，不確定的地方列在 §8。

## 6. 附件

- 讀進來一個對話時，附件隨它一起讀（現在的行為，只是範圍從「全部對話」變成「這個對話」）。
- 之後（P6，選做）：同一個對話裡的附件再延後到訊息真的顯示或送出時才讀。這要改約 23 個直接讀 `inlineData.data` 的檔案，只有很大的對話才有意義，先不做。

## 10. 風險與對策

| 風險 | 對策 |
|---|---|
| 漏改某個讀 `.messages` 的地方，讀到空訊息 | 凍結空陣列（寫入丟錯）、存根標記、儲存拒絕存根、掃描測試；旗標關閉時行為與現在完全相同 |
| 持有舊陣列引用跨 `await` 後被收回 | 收回條件保守（見 §3.3）；收回只在閒置時；hydrate／收回都就地 |
| 雲端同步在存根上算錯 | P0 先讀完；P5 才碰；同步的現有測試（含 journal 逐步比對）全部要在存根模式下再跑一次 |
| 啟動讀 N 筆小記錄比讀一筆慢 | P0 壓測先量（1500 筆小記錄的 `readItems`）；若慢就把存根分組成每 50 個一筆 |
| 補寫存根期間資料不一致 | 存根記錄與對話記錄在同一交易寫；補寫只加不改；完整性檢查把「有 `stub` 旗標卻沒有記錄」當可修復 |
| 退不回 | 舊程式忽略新欄位（P0 實測）；`?ws3=0` 關掉旗標後 `load()` 走原路，存根記錄留著不影響 |
