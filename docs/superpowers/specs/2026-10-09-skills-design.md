**日期：** 2026-10-09

## 0. 摘要

| 項目 | 建議 |
|---|---|
| 是什麼 | 「教模型怎麼做一件事的說明與流程」。和命令工具（可以執行的程式）不同，不混在一起 |
| 格式 | 相容公開的 Agent Skills 格式：一個資料夾，裡面一份 `SKILL.md`（開頭的 YAML 標頭有 `name`、`description`，下面是 Markdown 本文），之後可以附 `scripts/`、`references/` |
| 怎麼進到模型 | 逐步載入：提示詞裡只放每個技能的「名稱＋一行描述」；模型判斷用得到時，才用工具 `load_skill` 載入全文。使用者也可以用 `/` 直接指定 |

| 不做 | 技能互相呼叫、排程觸發、技能市集分享（P1 到 P3 都不含） |

## 1. 目標與非目標

**目標**
- 使用者加入一個技能後，模型在適合的時候自己照它的做法做，或使用者用 `/` 明確指定。
- 技能內容不吃掉上下文：裝很多個也只佔一點提示詞。
- 技能跟著帳號走（換裝置還在），本機與伺服器兩種回覆執行位置都能用（同一份程式碼，不寫兩套）。
- 技能是會進模型提示詞的文字，安裝前使用者一定看得到全文。

**非目標（P1）**
- 執行腳本、連網、讀寫使用者檔案（P2 才做，且重用命令工具的沙盒與權限）。
- 使用者上傳整個資料夾或 zip（P1 只收一份 SKILL.md 的文字）。

## 2. 資料格式

沿用公開格式的限制（讓使用者從別處拿到的技能能直接用）：

- `name`：1～64 字，小寫英數字與連字號，不以連字號開頭或結尾；是技能的 id，也是 `/name` 的名字。
- `description`：1～1024 字，講「做什麼、什麼時候用」。模型靠這句決定要不要載入，寫不好就不會被用到。
- 本文：Markdown，P1 上限 20,000 字元（約 5,000 token；公開建議也是這個量級）。
- 選填標頭（`license`、`compatibility`、`metadata`、`allowed-tools`）讀進來但 P1 不使用；不認得的欄位忽略，不報錯。
- 顯示用名稱與多語言描述：官方技能可以另外提供各語言的顯示名與描述（`i18n`，放在我們自己的目錄檔，不在 SKILL.md 裡）；使用者自己貼的技能就顯示 `name` 與 `description` 原文。

## 3. 來源與儲存

| 來源 | 內容放哪裡 | 說明 |
|---|---|---|
| 官方技能 | `src/data/skill-catalog.js`（像 `cli-catalog.js`，客戶端與伺服器共用，列進 `scripts/server-shared-modules.json`） | owner 上架；內容隨版本發布，不需要資料庫 |
| 使用者自己加入的技能 | 新的 Supabase 資料表 `user_skills`（`user_id`、`name`、`description`、`body`、`created_at`、`updated_at`，列層級安全性只讓本人讀寫） | 本文可能很長，不放進設定物件（設定是整份一起同步，加上逐項時間戳合併，塞長文字會拖慢） |

「已啟用」與「允許模型自己使用」這兩個清單放在設定裡，跟命令工具一模一樣（`skillEnabledIds`、`skillModelUseIds`，逐項時間戳合併，沿用 `cli-settings-merge.js` 的做法）。官方技能預設「允許模型自己使用」為開，使用者自己貼的技能也預設為開（因為安裝時已經看過全文並確認，見 §6）；使用者隨時可以關。

## 4. 模型怎麼用到技能

1. **提示詞裡的清單**：送出訊息時，把「已啟用且允許模型使用」的技能列成 `- name: description`（最多 30 個，每條描述截到 300 字；超過時只放最近加入的並在設定頁提醒）。一句固定說明：「需要時用 `load_skill` 取得完整說明，不需要就不要載入。」
2. **`load_skill(name)` 工具**：回傳該技能的本文（超過上限的截斷並註明）。放在共用的工具迴圈裡，本機回覆與伺服器回覆走同一份程式碼。一次回覆最多載入 5 個技能，同一個技能只載一次。
3. **使用者用 `/` 指定**：訊息開頭或空白後輸入 `/` 叫出清單，選了在輸入框放一個晶片（和 `@` 命令工具的晶片同一套元件）；送出時，這個技能的本文直接放進這則訊息的提示詞（不經過 `load_skill`），並告訴模型「使用者明確要求使用這個技能」。
4. **不套用「判斷模型」（Decisions）**：判斷模型負責網頁搜尋、檔案指引這類，技能是模型看描述自己選，不另外加一層。
5. **處理時間顯示**：載入技能算一個步驟，顯示在回覆的處理時間裡（「載入技能：寫作潤飾」），讓使用者知道模型用了哪個。

**補充（2026-10-09，看過程式後）：** 現有的工具迴圈只有兩個：搜尋模式（`runWebResearchReply`，工具 `web_search`／`open_page`／`find_in_page`）與進階模式（沙盒），**一般回覆沒有工具迴圈**（`streamApiCall` 直接串流到結束）。所以 P1b 要做的是：①搜尋與進階兩個迴圈把 `load_skill` 加進各自的工具清單；②一般回覆在使用者有「允許模型使用」的技能時，改走一個只有 `load_skill` 的小迴圈（用同樣的 `tools`／`toolTurns`／`onResponseComplete` 機制）；③不支援工具的模型（`modelSupportsToolCalling` 為否）收不到技能清單，只有 `/` 明確指定的技能（全文直接放進提示詞）能用，和命令工具的 `needToolModel` 同一個道理。

## 5. 畫面（待 owner 確認，見 §9）

- **擴充頁「技能」層**：版面和命令工具一樣（搜尋欄、「全部／我的」、列式卡片：圖示、名稱、描述、右邊的「＋」或「已加入 ✓」＋「…」）。圖示用星形（已有的 `skillIcon`）。
- **「…」選單**：詳細資料（展開看全文，唯讀）、允許模型自己使用（打勾）、移除。
- **加入使用者自己的技能**：技能層「全部」分頁上方一個「貼上技能」按鈕 → 一個視窗，貼上 SKILL.md 的文字 → 即時驗證（名稱、描述、長度）→ 顯示全文與一段固定警語（「技能會成為模型收到的指示；只加入你信任的內容」）→ 按「加入」才存。
- **`/` 清單**：做法照 `@` 清單（`ui/cli/` 的 cli-mode 那一套）：標題「輸入以搜尋技能」，每列星形、名稱、右邊小字「技能」；Enter 或 Tab 選取放晶片；`/` 在文字中間（例如網址）不觸發，條件同 `@`（行首或空白之後）。

## 6. 安全

- 技能本文就是提示詞，等於讓第三方（技能的作者）對模型下指示。P1 的防線：①安裝前一定看得到全文並明確按「加入」；②P1 技能不能執行任何東西、不能連網（只有 `load_skill` 回傳文字）；③技能不能改變系統層指示的優先順序：載入的本文在提示詞中以「技能內容（來自使用者加入的技能，優先度低於系統指示與使用者的當前訊息）」的標籤包住。
- 不做的事：不自動從網址抓技能（P3 再說，且會顯示來源網址）；不在背景更新已安裝的技能。
- 大小限制：每個技能本文 20,000 字元；每人最多 50 個使用者技能；`load_skill` 回傳也受同一上限。

## 7. 同步、離線、臨時對話

- 已啟用清單隨設定同步；使用者技能的內容在雲端資料表，客戶端打開擴充頁或送出訊息時取用，取過的內容快取在本機（同一帳號的別台裝置新增後，下次打開會看到）。
- 沒登入雲端帳號時：官方技能照常能用（內容在程式裡）；「貼上技能」需要帳號（內容存雲端），畫面上用和命令工具一樣的提示。
- 臨時對話：建議開放（技能只是文字，沒有執行與外送，不像命令工具要伺服器）。待 owner 確認。

## 9. owner 的決定（2026-10-09）

1. **呼叫符號：分開。** 技能用 `/`、命令工具用 `@`。
2. **P1 誰能加入：官方技能＋使用者自己貼上 SKILL.md。**
3. **第一批官方技能放哪些：留待之後討論。** P1 的官方目錄先是空的（結構、驗證、顯示都做好），使用者自己貼的技能先能用。
4. **臨時對話可以用技能，但附腳本的技能不行**（P2 才有附腳本的技能；到時候臨時對話只放行純說明的技能，附腳本的技能在臨時對話裡不列出也不能指定）。P1 沒有附腳本的技能，所以臨時對話全部放行。
5. **使用者貼上的技能預設「允許模型自己使用」：開。**

## 14. P2 設計：技能附檔案與腳本（2026-10-09，等 owner 確認；owner 已決定「上傳 zip」）

**目標。** 一個技能可以是一個資料夾：`SKILL.md` 加 `references/`（模型要讀的長說明）、`scripts/`（模型要執行的腳本）、`assets/`（範本等小檔案）。使用者上傳一個 zip，之後和純文字技能一樣用 `/` 指定或讓模型自己載入。

### 14.1 技能包格式與限制

- zip 的根目錄直接是 `SKILL.md`，或只有一層資料夾、裡面是 `SKILL.md`（公開技能多半是這樣，兩種都收）。其他檔案放在底下任意子資料夾。
- 限制（頁面上傳時檢查，伺服器存之前再檢查一次，同一份 `src/data/skill-bundle.js` 共用）：zip 本身 ≤ 5 MB；展開後 ≤ 10 MB；≤ 60 個檔案；路徑 ≤ 200 字、不可含 `..`、絕對路徑、反斜線或隱藏資料夾（`.git` 等，直接略過不收）；單檔 ≤ 2 MB；不收符號連結。
- 腳本只認兩種：`.py`（Python 3）與 `.sh`。其他可執行格式（`.exe`、`.so`、`.js` 等）仍可當檔案存放，但技能詳細資料會標出「不能執行」，模型也被告知不能執行。P2 的沙盒本來就只有 Python 與命令列。
- `SKILL.md` 本文限制不變（20,000 字元）。`allowed-tools`、`license`、`compatibility` 讀進來顯示在詳細資料，**不生效**：公開格式的 `allowed-tools` 是 Claude Code 的工具名稱，我們的沙盒沒有那套；腳本能做什麼完全由沙盒本身的規則決定（沒有網路，除非使用者在命令工具那邊授權的網路規則），這比逐項放行更保守。

### 14.2 儲存

- 新的私有儲存桶 `user-skill-bundles`，路徑 `<user_id>/<name>.zip`（驗證後的 zip 原樣存，伺服器讀時才展開，不拆成很多筆資料列）。只有本人能讀寫自己的路徑（儲存桶的列層級政策），伺服器用服務角色。
- `user_skills` 加兩個欄位：`file_count integer not null default 0` 與 `files jsonb not null default '[]'`（路徑、大小、種類的清單，給列表與詳細資料顯示，不必下載 zip）。`body` 仍存 `SKILL.md` 的本文。刪除技能時一併刪 zip（伺服器的清理掃描 `asset-sweeper.js` 要認得這個儲存桶的孤兒）。
- 換裝置：頁面開擴充頁時讀 `user_skills`（含 `files` 清單）；zip 不下載，只有要在頁面這邊讀 `references/` 時才取。
- 沒登入雲端帳號：不能上傳（和貼上一樣，內容存雲端）。

### 14.3 模型怎麼用

1. `load_skill` 回傳本文後面多一段「這個技能的檔案」清單（路徑與大小，最多 60 行），說明哪些能讀、哪些能執行。
2. 新工具 `read_skill_file(skill, path)`：回傳 `references/` 與 `assets/` 裡一個**文字檔**的內容（≤ 20,000 字元，超過截斷並註明）。一般、搜尋、進階三種回覆都有，伺服器與頁面共用（像 `load_skill`）。一次回覆最多讀 10 個檔。
3. **執行腳本只在進階模式的伺服器沙盒**：技能被載入時，伺服器把整個技能資料夾唯讀掛載在沙盒的 `/skills/<name>/`（新的沙盒主機端點 `POST /v1/sessions/:id/skills`，作法同 `/cli`：由伺服器把檔案內容送給 runner，runner 寫進 session 資料夾後以唯讀掛載；和 `/opt/cli` 一樣，這個資料夾不加執行權限）。模型用既有的工具 `run_command` 或 Python 去跑：`python /skills/<name>/scripts/x.py ...`、`sh /skills/<name>/scripts/y.sh`。直譯器讀取檔案不需要執行權限，所以「`/tmp` 與 `/work` 不可執行」的規則不用放寬，也沒有任何模型自己寫的檔案能被執行的新路徑。
4. 瀏覽器內的 Python 沙盒（本機回覆）沒有 `/skills`：腳本不能跑，只有 `read_skill_file` 可用；技能的附腳本部分在清單的說明裡標「需要伺服器上的進階模式才能執行」。
5. 一般與搜尋回覆（沒有沙盒）：同上，只能讀文字檔。

### 14.4 安全

- 腳本是第三方寫的程式，風險比純文字高。防線：①上傳後的確認視窗列出所有檔案，可展開看任一個檔案的原文（腳本要標示），固定警語（「腳本會在沙盒裡執行；只加入你信任的來源」），按「加入」才存；②沙盒本身：沒有網路（除非使用者授權）、1 次最多 2 分鐘、唯讀掛載、不能執行模型自己寫的檔案、容器隨回覆結束消失；③**臨時對話不放行有腳本的技能**（owner 決定 4）：不列在清單、`/` 選單也不出現，純說明的技能照常；④技能的檔案**不**會自動執行，只有模型在回覆中明確呼叫 `run_command` 或 Python 才會；使用者在步驟列看得到每一次執行；⑤密碼與金鑰：技能腳本拿不到使用者的憑證，除非該技能同時在使用者授權的命令工具設定裡（P2 不做這件事，技能腳本一律無憑證）。
- 步驟列：新增「讀取技能檔案」一列（`read_skill_file`，星形圖示，和「載入技能」同一種），執行腳本照原本的指令列顯示。

### 14.5 畫面（要問 owner，見 §16）

- 技能層「全部」分頁上方：原本的「貼上技能」旁邊加「上傳技能包」按鈕（手機上兩個按鈕並排；位置照貼上按鈕）。
- 上傳後的確認視窗（沿用貼上視窗的版型）：左邊檔案樹或清單，右邊顯示選到的檔案原文；上面是技能名稱與描述；下面是警語與「加入」。
- 詳細資料：多一區「檔案」（路徑、大小，腳本有標籤），可點開看原文（唯讀）。
- 列表的卡片：有腳本的技能名稱旁一個小標「腳本」。

## 15. P3 設計：製作技能（2026-10-09，等 owner 確認；owner 的方向：「跟製作技能的技能一樣的邏輯」）

**方向。** 不做一個獨立的「技能編輯器」介面，而是用技能做技能：一個官方技能 `skill-creator`，教模型用**訪談 → 草稿 → 試用 → 修改**的流程和使用者一起做技能，做好後由一個工具把草稿交給使用者確認並存起來。這和 Anthropic 的 skill-creator 是同一套邏輯：先搞清楚意圖，寫草稿，用幾個真實的例子試跑，依回饋修改，直到使用者滿意。

### 15.1 官方技能 `skill-creator`（純文字，英文本文，五語標題與描述）

本文教模型：
1. **抓意圖。** 先從對話裡找答案（使用者說「把剛才的做法存成技能」就從歷史擷取：步驟、使用者的修正、輸入與輸出的樣子）。缺的再問，一次問不超過三個問題：這個技能讓模型做什麼、什麼時候該用、輸出長什麼樣。
2. **寫草稿。** 照 SKILL.md 格式：`name`（小寫連字號）、`description`（說「做什麼」與「什麼時候用」，寫得主動一點，列出使用者可能的說法，因為模型靠這一句決定要不要載入）、本文（祈使句、解釋「為什麼」而不是堆全大寫的規定、保持精簡、固定輸出格式用範本、需要時放範例）。
3. **試用。** 想 2 到 3 個使用者真的會說的測試問題，說出來讓使用者確認，然後自己照草稿做一遍給使用者看（沒有分身的環境，所以是同一個模型照技能做），請使用者評論。
4. **修改。** 依回饋改，重點是歸納而不是針對那幾個例子打補丁；重複做同樣事情的部分考慮放進腳本（有進階模式時，見 §15.3）。
5. **交付。** 呼叫 `propose_skill`。

### 15.2 工具 `propose_skill`（新）

- 參數：`name`、`description`、`body`；檢查和貼上視窗同一份規則（`skill-format.js`）。不通過就把原因還給模型讓它改。
- **模型不能直接存。** 工具的結果是：聊天室裡出現一張「技能草稿」卡片（名稱、描述、可展開看全文），上面兩個按鈕：「加入技能」（走和貼上視窗相同的存檔路徑，需要雲端帳號；已有同名技能時問是要取代還是改名）與「繼續修改」。使用者按了才存。這和 §6 的原則一致：技能是進模型提示詞的文字，一定要使用者看過全文並明確按下才加入。
- 只在這個回覆有 `skill-creator` 被載入時才提供（其他回覆沒有這個工具）。三種回覆迴圈都支援。
- 存好之後預設「已啟用、允許模型自己使用」，和貼上一樣。

### 15.3 把做過的流程存成技能（含腳本）

進階模式在伺服器沙盒裡跑出成果後，使用者說「把這個流程存成技能」：`skill-creator` 教模型回頭看這則回覆用過的腳本，整理成 `scripts/` 與 `SKILL.md`（本文寫「什麼時候、用哪個腳本、參數」）。實作上 `propose_skill` 多一個選填參數 `files`（路徑與內容，限制同 §14.1），內容來自模型當場寫出的文字；卡片上列出所有檔案讓使用者看，按「加入」就和上傳技能包走同一條存檔路徑。這一段排在 P2 之後。

### 15.4 不做

貼網址匯入：owner 沒有選，風險（抓取安全、授權）與工作量都最大，先不做。背景自動更新已安裝的技能：不做。

## 17. P2a 實作紀錄（2026-10-09）

- `src/data/skill-bundle.js`（頁面與伺服器共用，只在需要時載入 jszip）：`readSkillBundle(bytes)` 讀 zip 並檢查，成功回 `{ skill, files: [{ path, size, kind, bytes }], bundle }`，`bundle` 是用通過檢查的檔案重新壓的乾淨 zip（根目錄就是 `SKILL.md`），存的是這一份，不是原始上傳的 zip。限制照 §14.1：zip 5 MB、展開 10 MB、60 個檔案、單檔 2 MB、路徑 200 字。
- 和設計不同的一處：**程式與安裝檔直接拒收**（`.exe .dll .so .dylib .bat .cmd .com .msi .scr .app .apk .jar .bin .ps1 .vbs .lnk` 回 `blocked_file`），不是「存下來但標不能執行」。理由：技能是說明與輔助腳本，沒有任何理由帶程式；拒收比標示簡單，也少一種要向使用者解釋的狀況。
- 檔案種類：`script`（`.py`、`.sh`）、`text`（能以 UTF-8 解碼）、`binary`。隱藏檔與隱藏資料夾（`.git`、`.env`、`.DS_Store`）和 `__MACOSX/` 靜默略過；`..`、絕對路徑、`C:`、反斜線、符號連結、大小寫不同但同名的檔案都拒收。外面包一層資料夾的 zip（`my-skill/SKILL.md`）會自動拿掉那層。JSZip 本身讀 zip 時就會拿掉路徑裡的 `..`，所以這一項測的是路徑清理函式；其餘的檢查是第二層。

- **格式：** `skill-draft` 區塊裡，每個檔案放在一行 `=== 路徑 ===` 後面（三個等號、空格、路徑、空格、三個等號）；第一個是 `SKILL.md`（第一行可以省略：第一個標記行之前的文字就是 `SKILL.md`），之後是其他檔案，每個放全文。沒有這種行的草稿還是單一份 `SKILL.md`（P3a 的格式不變）。有檔案的草稿裡若有三個反引號的行，區塊用四個反引號開頭與結尾，不會提早結束（測試確認 marked 把它當成一個區塊、一張卡片）。`src/data/skill-draft.js`：`draftHasFiles`、`splitDraft`（路徑前後空白去掉、每個檔案結尾一個換行）、`readDraftBundle`（把草稿組成 zip，交給和上傳技能包同一個 `readSkillBundle` 檢查，所以拒收的原因和路徑都一樣：`blocked_file`、`bad_path`、`duplicate_path`、`skill_md_missing`，`SKILL.md` 的標頭規則同貼上的技能；`SKILL.md` 寫了兩次回 `duplicate_path`）。

- **沒有改動的：** 加入的路徑、儲存、`/skills` 掛載、臨時對話過濾都沿用 P2。草稿的腳本不會在加入前執行。

## 23. 孤兒 zip 的清理（2026-10-09）

帳號刪除時 `user_skills` 的資料列會跟著刪（`on delete cascade`），儲存桶 `user-skill-bundles` 裡的 zip 不會；上傳到一半失敗留下的 zip，或有人在自己的資料夾放的其他檔案，也沒有資料列指著它們。
- **`orphan_skill_bundles(older, limit)`**（`supabase/migrations/20261009030000_orphan_skill_bundles.sql`，已套用到專案）：列出儲存桶裡「沒有任何 `user_skills` 資料列的 `<user_id>/<name>.zip` 指到」而且最後更動時間早於 `older`（預設一天：zip 比它的資料列早一點上傳，所以年輕的檔案絕不算孤兒）的檔案。只有服務角色能執行（`anon`、`authenticated` 都不行）。用「會自動還原」的區塊驗證過：有資料列指著的、一天內的都不會列出，沒有資料列的 zip 與名稱不是技能的雜檔會列出，驗證沒有留下任何資料。
- **`server/skill-bundles.js` 的 `removeAll(paths)`**：用儲存 API 刪（同時釋放空間），只收「某人的資料夾加上名稱」的路徑，向上的路徑、反斜線、不在人的資料夾裡的都不收。
- **`server/asset-sweeper.js`**：每天一次的清理（伺服器啟動兩分鐘後第一次）在附件與回覆檔案那一輪之後，多一輪技能 zip；兩輪各自記錄、各自失敗不影響對方（`skill_bundle_orphans_found`、`skill_bundle_orphans_removed`、`skill_bundle_sweep_failed`）。**和原來的清理一樣，預設只報告不刪除，環境變數 `ASSET_SWEEP=delete` 時才真的刪**——所以第一次真正刪除仍是擁有者讀過報告後的決定。`sweepOnce()` 的回傳在原本的欄位之外多了 `bundles`（只有帶了技能 zip 的儲存時才有）。
- **測試：** `server-storage`（儲存的路徑規則、兩輪的報告與刪除、其中一輪失敗不影響另一輪、SQL 檔的重點）。

## 24. 第一批官方技能（開始於 2026-10-09）

做法（owner 決定，2026-10-09）：官方技能全部自己寫，一個一個來；每個先把草稿給 owner 看過，同意了才加進 `OFFICIAL_SKILL_CATALOG`。內文用英文（模型最穩，並規定「用使用者的語言回答」），標題與說明有五種語言。預設不預先加入，使用者在擴充頁按「＋」。寫法用「製作技能」的原則：說明要說「做什麼、什麼時候用」並寫得主動、解釋為什麼、保持精簡、固定格式用範本、一個小範例、缺資料時怎麼辦。

- **規則（有測試 `tests/official-skills.test.js`）：** 每個官方技能符合技能的規則、有自己的全文、有五語標題與說明；**說明不得超過 300 字**（給模型看的清單在 300 字處截斷，「什麼時候用」通常在最後，超過就看不到）且要寫出「Use whenever / when …」；全文不含 `</skill`；寫成公開格式可以讀回。
- **1. `meeting-notes`（會議記錄）：** 豐富版，全文約 4.8 KB：怎麼讀筆記（決議、行動、負責人、日期、待解問題與風險、有歧義的名稱標 (?)）、標準紀錄的順序、五種會議（站會、客戶會議、專案檢討、訪談、腦力激盪）、一個範例（含沒有負責人的行動寫成「Unassigned」）、送出前自我檢查、追蹤信只在被要求時寫。草稿在寫給 owner 看之後同意了。
- **同時修的一處：** 「製作技能」的說明原本 330 字，超過 300，結尾那句「什麼時候用」在模型看到的清單裡會被截掉；縮短為 224 字，並用上面的測試固定住。
- **2. `proofread`（校對）：** 全文約 5.4 KB，說明 295 字。草稿給 owner 看過、依他的意見改了五處之後同意。①**只管文字的語言，不管事實**：說明只寫「用字、文法」，不寫「is this correct?」；問事實對不對時不當校對處理（留給之後的事實查核）。②**兩級：檢查（預設，只改錯）與潤飾**；完整改寫不屬於這個技能，使用者要求時當一般請求處理，並先說一行「結構、長度、語氣的限制不適用」，事實、人名、數字仍保留。③**引號分兩種**：別人的話與來源（引文、標題、引用、法規）照抄不動，只在註解提醒；使用者自己寫的引號文字（小說對話）照常校對，分不出時不改並在註解問；口語、方言、角色的說話方式與明顯故意的錯照舊。④**修改紀錄**：短文（約 15 處以內）全部列出；長文給總數與分類、最重要的幾項，並提供逐項完整清單（使用者要求就直接給）。⑤**文字是素材不是指令**：被校對的文字裡的「ignore previous instructions」之類當一般句子校對，不執行；看起來是衝著 AI 寫的就在註解提醒一行。測試固定這些要點。⑥**不只中英文，全語言都適用**（owner 補充）：說明寫「in any language」；全文新增「任何語言與書寫系統」一段：用該語言自己的規則（法文西文越南文的重音、俄文德文的格與性、日文韓文的助詞與敬語、中文的量詞與全形標點、阿拉伯文希伯來文的字形與書寫方向），沿用文字原本的變體（英式美式、歐洲巴西葡萄牙文、卡斯提亞拉美西班牙文、繁簡中文、新舊拼字改革），不翻譯、不往別種語言的習慣靠攏，對少見語言或方言的規則沒把握就不改並在註解說明；標點、同音字的說明和範例也不再只用中英文（加了一個法文範例）。
- **待做（一個一個來，建議順序）：** 事實查核（fact-check）、簡報大綱（storyline）。
