## 1. 目標與非目標

**目標**
- 使用者送出訊息後關閉分頁或手機鎖屏，回覆仍會完成，重新打開時看得到完整結果與過程。
- 同一份程式碼（供應商請求、工具呼叫迴圈）在瀏覽器與伺服器兩邊都能跑，不寫兩套。
- 不改變現有的本機模式：伺服器不可用時自動退回本機，並明確告知。
- 為「技能腳本」與「命令列工具」準備一個可以隔離執行的地方（S2、S3）。

**非目標**
- 排程、事件觸發、常駐的個人代理（已放棄）。
- 讓伺服器長期保存使用者的模型金鑰（見 §6）。
- 把雲端同步資料庫搬離現有的託管服務。

## 2. 現況調查（這份計畫依據的事實）

調查範圍是目前的 `main`，以下是讀程式得到的結論：

1. **供應商請求與工具迴圈大部分不依賴 DOM。**
   - `src/app/legacy-runtime/features/stream-api-call.js` 的 `createStreamApiCall` 以注入方式取得所有環境（`getApiKeyForProvider`、`getConfig`、`getAstras`、`getPersonalMemories`、`getMemoryContext`、`fetchImpl` 等），整個檔案只有 2 處碰到 `window`／`document`。
   - `web-research-reply.js`（`runWebResearchReply`、`createResearchCalls`）、`tool-call-formats.js`、`model-request-formatting.js`、`provider-request-support.js`、`sandbox-reply.js`（`runSandboxReply`）幾乎沒有 DOM 相依；搜尋、開網頁、Python 沙盒都是注入的函式。
   - 所以伺服器可以直接重用這些模組，只需提供不同的注入值。
2. **UI 與迴圈的耦合集中在** `single-model-response-lifecycle.js`：它同時處理進度顯示、引用標記、處理步驟列。伺服器端需要一個不碰 DOM 的執行器，把同樣的事件改為寫入資料。
3. **回覆的過程資訊已經是訊息文字的一部分。** `src/app/ui/sandbox/sandbox-run-block.js` 的 `noureon-run` 區塊（步驟、來源、思考、狀態 `running｜done｜failed｜stopped`）隨訊息保存，客戶端依它畫出「處理過程」列與來源。因此伺服器只要寫出同格式的訊息，客戶端不用改就能顯示。
4. **雲端同步 V2 已有串流中的訊息。** `workspace_messages` 有 `status in ('streaming','complete','error')`，同一個訊息 ID 反覆更新（客戶端節流為 750 毫秒），其他裝置透過 Realtime 即時套用。訊息內容（`parts` jsonb）不是端到端加密。**伺服器寫入同一張表，已打開的頁面就會自動收到。**
5. **模型金鑰是端到端加密的。** 金鑰存在瀏覽器，同步時用使用者的「同步密碼」加密（`src/app/sync/sync-vault.js`，PBKDF2＋AES）。伺服器讀不到，這是優點，§6 的設計要保住它。
6. **檔案區塊由客戶端產生。** 模型輸出的 ` ```file ` 區塊在使用者預覽或下載時才在瀏覽器生成 docx／pptx／pdf，伺服器不需要生成這類檔案。只有 Python 產出的檔案（訊息 part `sandboxFile`）需要伺服器處理（S2）。
7. **看圖檢查（V1、B5）在客戶端執行**，伺服器端回覆不會觸發它（§10 已知限制）。
8. **Python 沙盒介面很小**：`prepare()`、`clear()`、`mount(files)`、`run(code, { signal })`（`sandbox-reply.js` 以 `getSandbox` 注入）。伺服器版本只要實作同一介面。
9. **目前伺服器端只有少量 Vercel 函式**（`api/`：搜尋與網頁讀取代理、網站圖示與名稱、NVIDIA 代理、同步金鑰庫救援、表單）。其中 `_site-fetch.js` 的「只允許公開網址、逐跳檢查轉址」邏輯可直接成為伺服器端 `open_page` 的 SSRF 防護。

## 3. 目標架構

```
 瀏覽器 (客戶端：組裝請求、顯示)            伺服器 (Zeabur 上的 Node 服務, api.noureon.com)
 ┌───────────────────────────┐   1. POST /v1/runs   ┌──────────────────────────────┐
 │ 組裝 RunSpec              │ ───────────────────▶ │ 驗證 JWT、檢查額度與大小      │
 │ （歷史、指示、記憶、金鑰） │ ◀─── 202 {runId} ─── │ 建立 run，金鑰只放記憶體      │
 │                           │                      │ 執行器：同一套 createStreamApiCall│
 │  Realtime 收到訊息更新 ◀───┼──── Supabase ◀──────┤   + runWebResearchReply        │
 │ （已存在的同步機制）       │  workspace_messages  │   (+ runSandboxReply, S2)      │
 │                           │  status=streaming…   │ 每 750 ms 寫回同一個訊息 ID    │
 │ POST /v1/runs/:id/stop ───┼────────────────────▶ │ 完成寫 complete；失敗寫 error  │
 └───────────────────────────┘                      └──────────────────────────────┘
```

**分工原則：客戶端是「大腦」，伺服器是「執行者」。**
- 客戶端照現在的方式組裝所有上下文（歷史、Noura 指示、記憶、檔案與圖表指引、搜尋設定），打包成 `RunSpec` 交給伺服器。伺服器不需要懂記憶系統、Noura 或設定，只負責「照這份規格把迴圈跑完」。
- 這樣新增功能時，客戶端的組裝邏輯只有一份。

## 4. RunSpec 與 API

**認證：** `Authorization: Bearer <Supabase access token>`。伺服器用 Supabase 的公開金鑰驗證簽章、取得 `user_id`；不信任請求內容裡的任何使用者 ID。

**`POST /v1/runs`**（回應 202）

```jsonc
{
  "protocol": 1,                    // 伺服器拒絕太舊或太新的版本，回傳 426 並說明
  "clientVersion": "17.4.0",
  "conversationId": "<uuid>",       // 必須屬於該使用者（伺服器查表驗證）
  "assistantMessageId": "<uuid>",   // 客戶端先產生，伺服器對它寫入
  "sequence": 12,
  "model": { "provider": "...", "id": "...", "info": { /* 模型註冊表的必要欄位 */ } },
  "request": {
    "history": [ /* 已套用 compactForApi 的歷史 */ ],
    "currentMessage": { "parts": [ /* 文字、小圖（上限見 §6） */ ] },
    "systemInstruction": "<客戶端組好的完整系統指示>",
    "generation": { /* 溫度、思考程度等 */ },
    "language": "zh-TW"
  },
  "tools": {
    "webSearch": "auto|forced|off",
    "searchProvider": "tavily|tinyfish",
    "advanced": false                // S2 起才可能為 true
  },
  "secrets": { "providerKey": "...", "searchKey": "..." }   // 只在這次請求，見 §6
}
```

**其他端點**
- `POST /v1/runs/:id/stop`：中止執行（用 `AbortController` 傳到供應商請求與工具）。
- `GET /v1/runs/:id`：狀態（`queued｜running｜done｜failed｜stopped`）、開始與結束時間、錯誤碼。
- `GET /healthz`：健康檢查，供 Zeabur 與客戶端判斷伺服器是否可用。

**錯誤碼要穩定**（客戶端據此顯示五種語言的訊息）：`unauthorized`、`conversation_not_found`、`too_many_runs`、`request_too_large`、`protocol_unsupported`、`provider_error`、`server_restarted`、`stopped`。

## 5. 資料與同步

- **訊息：** 伺服器以 `status='streaming'` 寫入同一個 `assistantMessageId`，節流與客戶端一致（750 毫秒），結束時寫 `complete` 或 `error`。`parts` 的格式與客戶端完全相同（包含 `noureon-run` 區塊、引用標記、檔案區塊文字）。
- **新資料表 `server_runs`**（遷移檔放 `supabase/migrations/`）：`id`、`user_id`、`conversation_id`、`message_id`、`status`、`stop_requested`、`model`、`created_at`、`started_at`、`finished_at`、`error_code`、`usage` jsonb。RLS：使用者只能讀自己的列；寫入只有伺服器。
- **伺服器的資料庫權限：** 使用服務金鑰，只放在 Zeabur 的環境變數。寫入前一律檢查「該對話屬於該 `user_id`」，且只能寫 `workspace_messages` 與 `server_runs` 的指定欄位，程式內集中成一個小模組，方便審查。
- **客戶端的接續：** 打開對話時若有 `server_runs.status='running'` 的列，介面顯示「伺服器處理中」，訊息內容由同步更新；使用者按停止就呼叫 `/stop`。
- **一個訊息 ID、一個寫入者：** 伺服器執行期間客戶端不得對該訊息寫入（避免互相覆蓋）；同步引擎已對相同 ID 以較新 `updated_at` 為準，仍須在測試中涵蓋。

## 6. 安全

1. **金鑰不落地。**
   - 客戶端在送出時才把這次需要的金鑰放進 `secrets`（走 HTTPS）。伺服器只存在該次執行的記憶體裡，結束即丟棄，**不寫入資料庫、檔案、日誌**。
   - 所以端到端加密的金鑰庫不受影響；代價是伺服器無法在使用者離線時自己開始新的工作（本計畫不做排程，所以沒有影響）。
   - 日誌規則：不得記錄請求內文、`secrets`、供應商回應內文；只記錄 runId、使用者 ID 的雜湊、狀態、耗時、錯誤碼。
2. **伺服器重啟時執行中的回覆會失敗**（金鑰在記憶體，沒有保存）。對應訊息被寫成 `error`，錯誤碼 `server_restarted`，客戶端提示「請重新送出」。這是刻意的取捨，比保存金鑰單純安全。
3. **額度與上限（初始值，S1 實測後調整）：** 每位使用者同時最多 2 個執行；單次最長 30 分鐘；工具呼叫上限沿用 20；請求大小上限 25 MB；每位使用者每分鐘最多 10 次建立請求。
4. **網路請求防護：** 伺服器端 `open_page`、搜尋一律走「只允許公開網址、每一跳轉址再檢查」（沿用 `_site-fetch.js` 的邏輯，改為共用模組）；逾時與大小上限同現有。
5. **CORS：** 只允許 `https://noureon.com`、`https://www.noureon.com`（與開發用 localhost）。
6. **提示詞注入：** 本階段（只有搜尋與開網頁）模型沒有可造成外部影響的工具，風險限於「被網頁誘導輸出」。從 S2 起，執行腳本與（S3）命令列工具涉及外部影響，必須有：預設不連外網、寫入或危險動作要使用者確認、祕密不進沙盒（S3 另行設計）。
7. **傳輸與管理：** 全程 HTTPS（Zeabur 自動憑證）；SSH 改金鑰登入、關閉密碼、機器防火牆只留需要的埠、安裝防暴力破解工具；定期快照（S4）。

## 7. 沙盒（S2）

- 介面與現在的 `getSandbox` 相同（`prepare`／`clear`／`mount`／`run`），讓 `runSandboxReply` 不改就能用。
- 實作：每次執行開一個**用完即丟的容器**，限制 CPU、記憶體、時間、磁碟，預設無對外網路，映像檔含 Python 與常用套件。輸出檔案上傳 Supabase Storage（沿用現有的雲端資產機制），訊息 part 指向資產（`sandboxFile` 格式相容，需在 S2 開頭確認現有 part 的資產參照寫法）。
- **未驗證的關鍵風險：** Zeabur 管理的機器上，服務能不能即時開隔離容器、需要什麼權限。S0 先用一個最小的測試服務確認；若不行，備案是另買一台約 5 美元的小機器專跑沙盒，由伺服器服務呼叫它。計畫不依賴這件事在 S1 之前成立。
- 「完整技能支援」需要更完整的映像檔（辦公軟體、瀏覽器、Node、常用命令列工具），映像檔體積與維護是 S3 的工作。

## 8. 與技能、命令列工具的關係（S3 預告）

- 技能的資料格式、左側欄管理頁、`/` 呼叫、模型自主載入、安裝審核卡片，屬於另一份設計；此處只保證執行層：伺服器能在沙盒裡執行技能附的腳本與命令列工具。
- 命令列工具需要：沙盒依技能開放特定網域、使用者祕密保管處（執行時注入環境變數、模型看不到值）、寫入動作的確認機制。這些都等 S3 再詳細設計。

## 9. 部署與維運

- **程式位置：** 專案內新增 `server/`（Node，純 ES 模組），直接 `import` 現有的共用模組；為避免伺服器程式引入瀏覽器專用程式碼，S0 會加一個邊界檢查（類似 `check:legacy-runtime`）。
- **部署：** Zeabur 從 GitHub 部署；是否能指定子目錄或需另放 `Dockerfile`，S0 確認。環境變數：Supabase 服務金鑰、JWT 驗證用的公開金鑰、允許的來源。
- **網域：** 例如 `api.noureon.com` 指向這台機器；`run.noureon.com` 已用於瀏覽器內沙盒，不重複。DNS 與 Zeabur 的綁定步驟在 S0 交給使用者做。
- **版本相容：** API 帶 `protocol` 版本；客戶端與伺服器各自可獨立更新。伺服器不可用或回 `protocol_unsupported` 時客戶端退回本機並顯示原因。
- **備份：** 伺服器上沒有不可重建的資料（程式在 Git、資料在同步資料庫），所以只需要在重大變更前手動拍快照。若 S2 之後機器上出現不可重建的資料，再補買整機備份。
- **監控：** `/healthz`、執行數、失敗率、記憶體；S4 做簡單的狀態頁與錯誤通知。

## 10. 階段（一次只做一個，每階段完成後回報，由使用者決定是否推 `main`）

| 階段 | 內容 | 驗收 |
|---|---|---|
| **S0 打底** | 抽出共用模組並確認 Node 能載入；`server/` 骨架、`/healthz`、JWT 驗證、`/v1/whoami`；`RunSpec` 的 JSON 驗證與測試；邊界檢查；Dockerfile；部署到 Zeabur、綁網域與 HTTPS；用最小服務測試「能否即時開容器」（決定 S2 路線） | 從瀏覽器帶登入權杖呼叫 `/v1/whoami` 成功；錯誤權杖回 401；測試與邊界檢查通過 |
| **S1 伺服器回覆** | 執行器（供應商請求＋搜尋工具迴圈、停止、額度）；寫入 `workspace_messages` 與 `server_runs`（含遷移檔）；客戶端送出路徑、設定開關、退回本機、處理中狀態、重新打開接續；五種語言文字；`PRIVACY.md` 更新；更新日誌 | 送出後關閉分頁，重新開啟看到完整回覆；兩台裝置同時開啟時另一台也即時看到；停止有效；伺服器重啟的回覆顯示可重送；用真實模型金鑰由使用者驗證 |
| **S2 程式執行** | 容器沙盒（Python），輸出檔案進雲端資產；`runSandboxReply` 在伺服器上運作；限制與清理 | 進階模式的回覆在伺服器上完成並產出可下載檔案；超時、超記憶體被終止且訊息有明確原因 |
| **S3 技能與命令列工具** | 另一份設計的實作：技能功能（左側欄管理頁、`/`、自主載入、網址與對話製作、工作流存成技能）、伺服器上跑腳本與命令列工具、祕密保管處、網域白名單、寫入確認 | 見該設計 |
| **S4 維運** | SSH 金鑰與防火牆、防暴力破解、快照流程、監控與狀態頁、log 保留 | 清單逐項打勾 |
| **（之後）** | 網頁推播（回覆在關閉頁面時完成會通知）；伺服器回覆完成後的看圖檢查 | 另行討論 |

**已知限制（S1）：** 伺服器端回覆不觸發看圖檢查；伺服器重啟時進行中的回覆需要重新送出；不能在使用者離線時自己開始工作。

## 11. 待決定（請使用者確認，我有建議）

1. **金鑰只在請求中傳遞、不保存（§6-1）**——建議採用。
2. **設定位置：** 在設定的哪一頁放「在伺服器上執行回覆」開關，預設開或關？建議預設**開**（兩個人使用，退回本機仍有保障），放在現有的「模型管理」旁的新區塊；介面請使用者看過樣式再定。
3. **伺服器重啟時進行中的回覆直接失敗並可重送**——建議採用（簡單、金鑰不落地）。
4. **S0 先做哪個網域名稱**（例如 `api.noureon.com`）。
5. **是否同意 S0 加「共用模組邊界檢查」**——避免伺服器不小心引入瀏覽器程式碼。
6. 每位使用者同時 2 個執行、單次最長 30 分鐘是否合理（目前只有 2 個使用者，建議先維持）。

## 12. 尚未驗證的假設

- 共用模組在 Node 中能完整載入（有些檔案以 `/src/...` 絕對路徑引入，S0 先確認）。
